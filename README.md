# 会员行为日志接入管道

把上游调度投递到 `inbox/` 的批次 CSV 幂等接入 `data/warehouse.db`，每次运行结束生成
对账报告 `report.txt`。

## 运行

脚本按既有约定从仓库根目录运行，路径默认是相对路径：

```bash
python3 ingest.py                 # 接入 inbox/ 下新到的批次，写 report.txt
python3 ingest.py --verbose       # 同时输出每批明细日志
python3 ingest.py --inbox /path/to/inbox --db /path/to/warehouse.db --report /path/to/report.txt
```

退出码：`0` 全部成功；`1` 有批次校验/接入失败（其余批次照常接入）；`2` 管道无法启动
（目录不存在、另一个进程持锁）。

## 输入格式

UTF-8 带表头，字段固定为 `event_id, member_id, event_time, event_type, amount_orig,
amount_cny, batch_date`（允许带 BOM）。整文件只允许一个 `batch_date`。

以下情况整批拒绝（不写任何行），原因进报告，修好文件后直接重跑即可：
表头缺字段、字段为空、金额不是有限数字、`batch_date` 不是合法 `YYYY-MM-DD`、
文件内 `batch_date` 不一致、文件无数据行。

## 幂等是怎么保证的

上游会重投批次：可能同名，可能带 `_r1` 之类后缀，也可能整目录重跑。管道分三层挡住：

| 层 | 机制 | 挡住什么 |
|---|---|---|
| 1 | 批次内容指纹（逐行规整排序后 sha256，登记在 `ingested_batches.content_sha256`，带唯一索引） | 改名重传、同名重传、目录重跑——内容一致就整批跳过，不重复入库 |
| 2 | `events(event_id)` 唯一索引 + 写入前逐行比对 | 指纹没命中的重投（例如重投文件多了几行）——只补库里没有的 `event_id` |
| 3 | 单批 `BEGIN IMMEDIATE` … `COMMIT` | 中途失败——整批回滚，不留半个批次 |

指纹按**数据内容**计算（行序、行尾空白、换行符差异不影响判定），所以上游重排行序的
重投也会被识别为同一批。

第 2 层顺带处理一种情况：同一 `event_id` 在两个批次里载荷不同（例如 11-10 的批次里
带了 11-08 的旧事件但金额不同）。管道保留**先到的版本**，后到的行不写入，并在报告
"事件冲突"小节列出，供财务核对。

## 水位与晚到批次

水位 = 已接入的最大 `batch_date`，存在 `pipeline_state.batch_date_watermark`（老库没有
这张表时从 `ingested_batches` 的最大 `batch_date` 接上）。

**水位只用于展示进度，不用于判定"是不是新批次"。** 上游不保证顺序，晚到的批次
`batch_date` 可能早于当前水位（例如 `batch_20251104_late.csv` 在 `2025-11-05` 之后
到达）。若按 `batch_date > 水位` 过滤，这类批次会被永久漏掉。所以新批次一律按内容
指纹判定，晚到批次照常接入并在报告里标注"晚到"。

## 对账报告 report.txt

每次运行结束写一份（原子替换，不会留下半截文件），含：

- 本次扫描的每个文件：批次日期、读取行数、新接入行数/金额、跳过行数、冲突行数、状态
- 本次合计（新接入行数与金额）
- 晚到批次明细
- 事件冲突明细（前 50 条）
- 失败批次及原因
- 累计对账：水位变化、全库累计行数、累计金额合计

金额一律用 `Decimal` 累加后按 2 位小数输出——SQLite 的 `REAL` 求和会出现
`0.30000000000000004` 之类的末位漂移，财务对账不能接受。

## 库结构

历史库是老工具建的，`events` 上没有唯一约束。管道启动时会就地迁移（不动已有数据）：

- `events`：补 `ux_events_event_id` 唯一索引。若历史库已有重复 `event_id` 导致建索引
  失败，降级为应用层去重并打 ERROR 日志（不静默跳过）。
- `ingested_batches`：补 `content_sha256`、`rows_inserted`、`rows_duplicate`、
  `rows_conflict`、`amount_cny` 列，并补 `ux_batches_sha` 索引。
- `pipeline_state`：键值表，存水位。新建。
- `batch_attempts`：重投/损坏/失败的尝试台账（主键 `batch_file + content_sha256`，
  `attempts` 累计次数）。成功接入后对应记录自动清掉。新建。

`ingested_batches` 只登记成功接入的批次；重投跳过、校验不通过、接入失败的记在
`batch_attempts`，不污染接入账本。

## 并发

同一库上的并发运行会被拒（`data/warehouse.db.lock` 上的 `flock`，后来者直接退出
返回码 2）。调度器重叠触发时不会出现两个进程交错写同一批。

## 测试

```bash
pytest -q tests/
```

36 个用例，覆盖：

- 重名重传 / 改名重传 / `_r1` 后缀 / 行序重排 / 目录重跑 均不产生重复
- 部分重叠的重投只补新行；库里 `event_id` 始终唯一
- 晚到批次（`batch_date` 早于水位）照常接入；水位只升不降
- 老库接续：从旧四列 `ingested_batches` 读水位、补列建索引
- 事务性：注入写入中途异常，验证整批回滚、无残留，且修好后可重跑
- 各类坏数据整批拒绝、失败批次不影响其他批次、退出码
- 报告金额精确（`Decimal`）、无新增时的报告、原子写
- 并发持锁拒绝
- 真实样例全量跑一遍（在 `tmp_path` 副本上，不污染仓库）

## 已知取舍

- 冲突行（同 `event_id` 不同载荷）**保留先到版本**，不做"以新覆盖旧"的更新。若业务
  需要以最新批次为准，需另加更新策略并留审计轨迹。
- `events` 保留历史表的宽松列定义（金额是 `REAL`），没有改成定点数存储。报告口径已
  用 `Decimal` 兜住，但要根治金额精度需要改表结构与历史数据迁移，属于单独一件事。
